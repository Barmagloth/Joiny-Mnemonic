# Roadmap — 2026-07-18

Цель: доказанный центральный сценарий (постфактум-финализация) на закрытом
транзишен-каркасе, с настоящим gate и dogfood. Только необходимое; всё
остальное — вне этого файла. Основание: аудит переходов состояний
(HANDOFF2, ред. 2; пробы H1–H10) и readiness statement в TODO.md.

## Модель (закреплено)

- **Workstream** = `TaskManager` / `task_versions` — рабочий поток
  (ветка, снапшоты, статусы active/blocked/completed/cancelled).
- **Obligations** = блок `open_tasks` + `memory_records(type=task)` —
  обязательства внутри потока.
- **Settlement** = переходы обязательств: candidate ledger,
  `kind=task_closure|block_change`, каркас `settle_candidate`
  (flow + терминалы + идемпотентность + trust + evidence).
- Связь: **Workstream нельзя завершить при активных Obligations без явного
  override**; автозавершения Workstream от закрытия последнего обязательства
  НЕТ (в обе стороны только явные переходы).

Это разные сущности с разной строгостью — по аудиту так и есть в коде;
roadmap делает различие осознанным, а строгость — одинаковой.

## Этап 1. Закрыть дыры переходов (п.3, п.4) — первым, всё остальное на нём

1. Один источник trust-значений: единая константа реально порождаемых
   origin рядом с `origin_evidence_type` (provenance.py:24-42); убрать
   4 разошедшиеся копии множеств (storage.py:3698, 3734, 4249, 4316) и
   мёртвые значения `signed_host_receipt`, `external_trusted_ui`.
2. Legality + терминалы + идемпотентность по образцу `_SETTLEMENT_FLOW`
   (storage.py:4304-4310) для:
   - `transition_candidate` — закрывает H1 (rejected→confirmed),
     H2 (confirmed→auto от untrusted);
   - `transition_finding` — закрывает H4 (дубль acknowledged),
     H5 (публичный ack-request де-acknowledge'ит finding);
   - Workstream `set_status` — закрывает H6/H7 (cancelled→active→completed
     без гейта через MCP/HTTP/CLI; статус влияет на prune-защиту
     снапшотов, storage.py:2741-2749).
3. Trust + evidence для Workstream-переходов: завершение/отмена/реанимация
   требуют derived trusted origin и собственного события перехода
   (не переиспользованного старого).
4. `find_auto_candidate_match` учитывает текущий статус кандидата —
   закрывает H3 (ре-подтверждение rejected через host-повтор факта).
5. Пиннинг-тесты H1–H9 из аудита кладутся в `tests/` и переворачиваются
   из «фиксируют дыру» в «фиксируют запрет».

Приёмка: пробы H1–H7 дают blocked; H8/H9 (строгость settlement) не
регрессируют; полный сьют зелёный.

## Этап 2. Связь Workstream × Obligations (п.1, п.2)

1. `complete(workstream)` проверяет открытые Obligations (строки
   `open_tasks` + незакрытые `task_closure`-кандидаты этой ветки) и
   fail-closed отказывает при непустом множестве.
2. Override — явный: отдельный аргумент/verb, trusted origin, собственное
   событие с перечнем перешагнутых обязательств; в остальном запрещено.
3. Обратного автозавершения нет: закрытие последнего обязательства не
   трогает Workstream (и наоборот).

Приёмка: тест «completed при открытом обязательстве» — отказ; тест
override — проходит и оставляет событие-обоснование.

## Этап 3. Постфактум-финализация (п.7) — центральный сценарий, P0

Существующие типы записей остаются: `Goal:`, `Decision:`, `Fact:`,
`Constraint:`, `TODO:`, `Preference:`, `Failure:`, `Lesson:`. Новое правило
относится не к типу, а к **моменту записи**: любой тип становится памятью
только после явной финализации решения. Экстрактор лишь обнаруживает повод
оформить или запросить подтверждение.

1. Грамматика финализации и статусы (CONFIRMED / rejected / deferred)
   поверх существующих типов; тег самодостаточен, id предложений —
   аудит-ссылки.
2. Принимается только из host-assistant finalization-события; цитаты,
   fenced-блоки, tool-output, retrieved, user-supplied — данные.
3. Материализация — через каркас Этапа 1: новый `candidate_kind`
   (например `finalization` — общий для всех типов записей) на существующем ledger'е, путём
   settlement (pending→applied/contested/reverted). Малформ/дубль/
   противоречие — fail-closed в quarantine.
4. Hard-filter непофинализированных предложений из resume/retrieval;
   транскрипт доступен только как данные по явному запросу.
5. Инструкции хостам (Claude Code, Codex): эмитить теги после решённого
   выбора; нет ответа — нет тега. Hostile E2E-фикстуры из TODO.md §0.

Приёмка: E2E: диалог → решение → тег → trusted память; все hostile-фикстуры
падают в quarantine, ни одна не материализуется.

## Этап 4. Настоящий benchmark gate (п.6) — до выбора backend

1. Неизменяемый артефакт: датированные подписанные отчёты
   (report_signing уже есть), `*-latest.json` больше не перезаписывает
   историю; фиксация «gate закрыт» — записью в ledger (kind
   `benchmark_gate`, pending→passed/failed/superseded), а не заголовком
   в markdown.
2. Точная идентичность испытуемой системы: extractor + model + prompt +
   config hash в `system_under_test`.
3. `PASSED` — только при машинной проверке
   `expected_target == report.system_under_test` (сегодня сравнения не
   существует; JSON-отчёты никто не читает — только пишут:
   benchmarks/extraction_gate.py:208, benchmarks/census.py:260).
4. Право закрыть gate — trusted origin (тот же список Этапа 1).

Приёмка: попытка объявить gate по отчёту с чужим/незаявленным backend —
машинный отказ; повторение июльского инцидента невозможно без подделки
ledger'а.

## Этап 5. Поставляемый экстрактор (п.5) — через gate Этапа 4

1. Зафиксировать требования (RU+EN, типы записей, precision/recall пороги,
   false-trusted=0, латентность/офлайн).
2. Короткие RU/EN-пробы кандидатов backend'ов (включая текущий
   nuextract-local — он не измерен) — research-статус, single-judge
   помечается явно.
3. Выбор backend закрывается только через gate Этапа 4 на согласованной
   цели. Роль экстрактора после Этапа 3 — детектор поводов, не источник
   trusted памяти.

Приёмка: запись `benchmark_gate: passed` с точной идентичностью выбранного
backend; словами «gate passed» без записи ничего не считается.

## Этап 6. Dogfood (п.8) — начинается сразу, не в конце

С момента закрытия Этапа 1 вести разработку Joiny-Mnemonic с включённым
Joiny-Mnemonic (hooks + resume + finalization теги в этом репозитории).
Каждая проблема реального использования — обязательство (Obligation) в
самой системе; исправления приоритезируются по реальным инцидентам, не по
списку фич.

Приёмка: N недель непрерывного использования; список инцидентов и их
закрытий читается из самой системы.

## Порядок и зависимости

1 → (2, 3 параллельно) → 4 → 5; 6 стартует после 1 и идёт фоном.
Вне списка ничего не делается, пока список не закрыт.
